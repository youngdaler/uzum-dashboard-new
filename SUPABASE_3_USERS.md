# Одна админ-панель для 3 пользователей — настройка Supabase

## Архитектура

Три отдельных аккаунта Supabase Auth (один владелец + два сотрудника) работают в одной базе данных: товары, партии, продажи, расходы, склад, финансы общие. Таблицы используют `user_id` владельца рабочей области. Доступ контролируется RLS, а не только интерфейсом. Учтите: **сейчас все трое имеют одинаковые права на просмотр, изменение и удаление данных**. Это не схема «админ + два пользователя с ограниченными ролями».

## 1. Supabase

1. Создайте проект на https://supabase.com/dashboard.
2. В **SQL Editor** запустите `supabase/migrations/0001_schema.sql`, а затем `supabase/migrations/0002_shared_workspace.sql` (если `0001` уже выполняли — выполняйте только `0002`).
3. В **Authentication → Users** создайте/пригласите три аккаунта с разными email и паролями. При регистрации через UI сначала убедитесь, что подтверждение email настроено. Для продакшена рекомендуется отключить свободную регистрацию, чтобы посторонние не могли создавать рабочие области.
4. Каждый аккаунт получит собственный workspace при создании. Затем **в SQL Editor под ролью администратора БД** свяжите два аккаунта с основным:

```sql
-- Замените email на настоящие. Сотрудники уже должны существовать в Authentication -> Users.
update public.workspace_members
set owner_id = (select id from auth.users where email = 'owner@example.com'),
    role = 'member'
where user_id in (select id from auth.users where email in ('staff1@example.com', 'staff2@example.com'));

-- Убедитесь, что видно три строки с одинаковым owner_id:
select m.owner_id, u.email, m.role
from public.workspace_members m join auth.users u on u.id = m.user_id
where m.owner_id = (select id from auth.users where email = 'owner@example.com');
```

Важное замечание: до присоединения к общей панели сотрудники могут создать личные данные. Они не перемещаются автоматически и после присоединения станут недоступны. Подключайте сотрудников **до использования приложения**.

## 2. Локальное окружение

Создайте `.env` в корне проекта:

```dotenv
VITE_SUPABASE_URL=https://YOUR-PROJECT.supabase.co
VITE_SUPABASE_ANON_KEY=YOUR_PUBLISHABLE_OR_ANON_KEY
```

Возьмите значения в Supabase **Project Settings → API Keys** / **Data API**. **Никогда не используйте `service_role` или secret key в клиентском `.env`.**

```bash
npm install
npm run dev
npm run build
```

При заданных переменных приложение использует Supabase. Если переменных нет, включается локальная демо-база **localStorage**, которая не синхронизирует данные между людьми.

## 3. Публикация сайта

Supabase здесь предоставляет БД и Auth, **но не хостит фронтенд Vite**. Разместите React-сайт на Vercel или Netlify; добавьте обе `VITE_...` переменные в настройки хостинга. Для React Router на Vercel используйте уже включённый `vercel.json`. В **Supabase → Authentication → URL Configuration** укажите адрес сайта как Site URL и при необходимости Redirect URLs для подтверждения email.

## 4. Синхронизация

При активной вкладке приложение загружает изменения других сотрудников примерно каждые 30 секунд, а также при возвращении к вкладке. Это **не realtime и не защита от одновременного редактирования одной записи**. Перед очень важными правками координируйте действия; для настоящего realtime/контроля конфликтов нужен дополнительный механизм.

## 5. Безопасность и права

- Все три пользователя пока имеют одинаковые права редактирования. Не выдавайте доступ посторонним.
- SQL-функции доступа и политики RLS проверяют связь с владельцем; чужие данные недоступны.
- Удаление аккаунта владельца приведёт к каскадному удалению его бизнес-данных; перед этим делайте резервные копии.
- Создание новых пользователей через регистрацию разрешается независимо от количества участников вашей панели. Ограничение **три** применяется к участникам **одного** рабочего пространства.
